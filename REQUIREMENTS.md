# ФинТрек — требования к новому проекту

Дата: 13 октября 2026 года. Версия документа: 1.0.

Статус: техническое задание MVP, реализация начата. Серверная часть на Go — обязательное требование владельца. Предыдущий Android-проект удалён; его архитектура и функциональность не являются требованиями к новой версии.

## 1. Цель и исходные решения

Создать небольшой, красивый и удобный трекер личных финансов. Первый продукт — адаптивный сайт и отдельный HTTP API, развёрнутые на собственном сервере владельца. Сайт должен быть пригоден для ежедневного использования с компьютера и телефона.

Приложением пользуется один владелец. Внутри можно создавать несколько именованных профилей с отдельными финансовыми данными. Создание профиля состоит из ввода имени; регистрация, почта и индивидуальные пароли не нужны. Профиль — отдельный набор данных, а не защищённая учётная запись.

В дальнейшем планируются приложение на Rust, мобильный клиент и автоматическое получение операций из банковских выписок, скриншотов или Android-уведомлений. Они должны использовать тот же API и правила расчётов.

В документе используются следующие обозначения:

- **MVP** — обязательная часть первого рабочего релиза.
- **Позже** — направление развития, не условие выпуска MVP.
- **Предложение** — технический выбор по умолчанию, который можно заменить до реализации с сохранением требований.

Основной принцип: сначала надёжный ручной учёт и приятный интерфейс, затем автоматизация. Архитектура должна позволять добавлять источники данных без переписывания финансового ядра.

## 2. Границы первого релиза

### 2.1. Входит в MVP

| Область | Результат |
| --- | --- |
| Профили | Создание по имени, выбор, переименование, независимые данные |
| Учёт | Один общий кошелёк на профиль, начальный остаток, доходы и расходы |
| Операции | Ручное создание, изменение и удаление; сумма, дата, категория, комментарий |
| Категории | Начальные категории, создание, редактирование и архивирование |
| Обзор | Текущий баланс, доходы и расходы месяца, расходы по категориям, последние операции |
| История | Поиск, фильтры, стабильная сортировка и постраничная загрузка |
| Бюджет | Общий месячный лимит и отдельные лимиты категорий расходов; остатки, прогресс и перерасход; дневной ориентир общего бюджета |
| Дизайн | Русский интерфейс, адаптивная вёрстка, светлая и тёмная темы, понятные состояния |
| Данные | Серверное хранение, CSV-экспорт операций, резервирование и проверяемое восстановление БД |
| API | Версионированный REST API, описание OpenAPI, проверка данных и единый формат ошибок |
| Сервер | Развёртывание через Docker Compose, постоянный том БД, миграции, health checks |

### 2.2. Не входит в MVP

Банковские интеграции, OCR, чтение push, нейросетевое распознавание, автоматическое создание операций, Rust-клиент, APK, iOS-клиент, офлайн-запись и синхронизация, несколько кошельков, переводы между ними, мультивалютность, конвертация, инвестиции, кредиты, долги, подписки, повторяющиеся операции, совместное редактирование и роли пользователей.

Финансовые цели, прогнозирование и PWA-установка также относятся к следующим этапам. Для MVP достаточно сайта, который удобно открывать в мобильном браузере.

### 2.3. Настройки по умолчанию

- Язык: русский; валюта: RUB; отображение: `1 250,50 ₽`.
- Часовой пояс профиля: `Europe/Moscow`, с возможностью выбрать другой IANA-пояс.
- Учёт ведётся по календарной дате операции, без обязательного времени суток.
- На профиль приходится один кошелёк «Общий баланс»; банковские карты отдельно пока не моделируются.
- Интерфейс открывает текущий месяц; баланс показывается за весь период учёта.
- Доступ только с сетью; браузер не является основным хранилищем финансов.

## 3. Пользовательские сценарии

### 3.1. Первый запуск и профили

Если профилей нет, показать приветствие, поле имени и кнопку «Создать профиль». После создания предложить начальный остаток и дату начала учёта; их можно пропустить, тогда остаток равен нулю, а начало учёта — первый день текущего месяца в часовом поясе профиля.

При создании сервер атомарно создаёт профиль, общий кошелёк и начальные категории. Повторное открытие сайта восстанавливает выбранный профиль по ID из локальной настройки браузера. С другого устройства доступны те же серверные профили.

Переключатель профиля всегда доступен. При переключении загружать только данные нового профиля, сбрасывать профильные фильтры и закрывать несохранённый редактор после предупреждения. Запоздалый ответ предыдущего запроса не должен появляться в интерфейсе другого профиля.

Имя: 1–50 символов после удаления внешних пробелов. Имена могут совпадать; идентификация всегда по UUID. Аватар в MVP — инициалы и цвет. Переименование не влияет на операции. Удаление профиля через UI и API в MVP не требуется.

Все профили доступны владельцу. Изоляция данных означает отсутствие случайного смешивания при запросах и расчётах; она не является разграничением доступа между реальными людьми.

### 3.2. Добавление операции

Из любой основной страницы доступна кнопка «Добавить операцию». В редакторе: переключатель «Расход / Доход», сумма, категория, дата и необязательный комментарий до 500 символов.

Дата по умолчанию — сегодня в часовом поясе выбранного профиля. Категории показываются только для выбранного типа. При смене типа несовместимая категория сбрасывается. Сумма положительная; знак определяется типом операции. Валюта в MVP фиксирована и не занимает отдельное поле ввода.

Сайт принимает точку или запятую как разделитель копеек. Поле суммы использует подходящую цифровую клавиатуру на телефоне. Ошибка находится рядом с полем и объясняет исправление. Во время сохранения повторная отправка заблокирована. После успеха закрыть редактор и обновить историю, баланс и бюджет. При сетевой ошибке сохранить введённые поля и предложить повторить.

### 3.3. Изменение и удаление

Нажатие на операцию открывает её детали и редактор. Изменения пересчитывают все связанные показатели. Перед удалением показать сумму и дату с явным подтверждением. После удаления операция не участвует в истории, балансе, экспорте и статистике.

Пользовательской корзины в MVP нет. В БД операция помечается удалённой, чтобы повтор запроса с тем же ID не создавал её заново. Восстановление отдельных удалённых операций через интерфейс не требуется.

### 3.4. Категории

При создании профиля подготовить расходы: «Продукты», «Кафе», «Транспорт», «Дом», «Здоровье», «Покупки», «Развлечения», «Другое»; доходы: «Зарплата», «Подработка», «Другой доход».

Категория содержит имя, тип, значок из встроенного набора и цвет. Имя — 1–50 символов; внутри профиля и типа оно уникально без учёта регистра и внешних пробелов. Тип после создания менять нельзя. Название, значок и цвет можно изменить: старые операции показывают обновлённое оформление.

Используемую категорию можно архивировать, но нельзя удалять физически. Она остаётся в истории и статистике, исчезает из выбора для новых операций. При редактировании старой операции её архивированную категорию можно сохранить; назначать архивированную категорию другой операции нельзя. Архивирование обратимо.

### 3.5. Месячный бюджет

Пользователь задаёт один положительный лимит расходов на выбранный месяц. Если лимита нет, показать «Бюджет не задан» и действие «Задать лимит», а не ноль процентов. Лимит не переносится на следующий месяц автоматически; можно предложить отдельную кнопку копирования прошлого лимита.

Показывать сумму лимита, потраченное, остаток, процент использования и дневной ориентир для текущего месяца. Перерасход отображается как отрицательный остаток и отдельный текст. Расходы остаются доступными даже после превышения лимита.

Бюджет — ограничение расходов, заданное пользователем. Он не равен балансу кошелька. Автоматический пересчёт остатка по записанным операциям входит в MVP; автоматическое получение банковских операций — следующий этап.

Для расходных категорий доступны отдельные положительные месячные лимиты, например «Кафе — 5 000 ₽», «Дом — 40 000 ₽». Они работают без общего бюджета и не изменяют его. По категории показываются фактические расходы, лимит, остаток, процент использования и положительная сумма перерасхода при отрицательном остатке. Без лимита соответствующие показатели равны `null`, а сумма перерасхода — `"0"`.

Сумма лимитов категорий может превышать общий бюджет: показать предупреждение и разрешить сохранить. Каждая операция учитывается один раз в общем бюджете и один раз в своей категории. Доходы и возвраты, записанные доходами, не уменьшают расходы. Изменение суммы, даты или категории операции и удаление пересчитывают оба уровня. Лимиты не переносятся автоматически между месяцами.

Архивирование категории сохраняет существующие лимиты и расходы. Изменение/удаление уже заданного лимита разрешены; создание нового для архивной категории требует восстановления. Версии продолжают расти при удалении и повторном создании, чтобы старая вкладка не перезаписала новый лимит.

## 4. Финансовые правила

### 4.1. Деньги

Все суммы хранить целым числом минимальных денежных единиц: для RUB это копейки. Поле БД — `BIGINT`; расчёты выполняются целочисленно. Не использовать `float`, `double` или JavaScript `Number` для денежных вычислений.

В JSON денежные поля передаются десятичными строками с суффиксом `_minor`, например `"amount_minor": "125050"`. Это 1 250,50 ₽. Такой формат применяется также к отрицательному балансу и результатам агрегирования; он не зависит от точности чисел JavaScript. На сайте использовать `bigint` или библиотеку точной десятичной арифметики. В API не принимать денежные JSON-числа.

Диапазон одной операции: от 1 до 99 999 999 999 копеек, то есть от 0,01 до 999 999 999,99 ₽. Начальный остаток допускает отрицательное значение в том же абсолютном диапазоне. Лимит бюджета положительный, в том же диапазоне.

Ввод `100`, `100,5`, `100.50` означает 100,00 / 100,50 / 100,50 ₽. Более двух знаков после разделителя, экспоненты, неоднозначные разделители и отрицательная сумма операции отклоняются; скрытого округления нет. API принимает только целые строки копеек, UI выполняет точное преобразование.

Для SQL-агрегатов использовать точную арифметику достаточной разрядности (`SUM(BIGINT)` в PostgreSQL возвращает `numeric`). Суммарные показатели не ограничивать максимальной суммой одной операции. На сервере проверять диапазон при сохранении каждой суммы.

### 4.2. Остаток и период учёта

Начальный остаток — деньги непосредственно перед началом даты `tracking_start_date`. Он не является доходом и не участвует в месячной статистике.

```text
Текущий баланс = начальный остаток
              + сумма всех неудалённых доходов с начала учёта
              - сумма всех неудалённых расходов с начала учёта.
```

Операция не может быть раньше даты начала учёта или позже сегодняшней даты профиля. Плановые операции появятся отдельно в будущем. Отрицательный баланс допустим и не блокирует записи.

Начальный остаток можно исправить в настройках; интерфейс поясняет, что это изменит общий баланс. Дату начала можно сдвинуть только если ни одна неудалённая операция не окажется до новой даты; иначе ответ `409`. Начальный остаток не должен автоматически подгоняться под расходы.

### 4.3. Периоды, статистика и бюджет

Операции содержат `occurred_on` типа `DATE`. Месяц определяется этой датой; например, октябрь — `[2026-10-01, 2026-11-01)`. Технические времена создания и изменения хранятся в UTC как `TIMESTAMPTZ`.

Изменение часового пояса влияет на «сегодня», начальный выбранный месяц и доступность будущих дат, но не переписывает календарные даты сохранённых операций. Уже записанные операции, ставшие будущими после смены пояса, остаются в учёте; запрет будущей даты проверяется при создании и изменении даты.

```text
Доходы месяца  = сумма доходов с occurred_on внутри месяца.
Расходы месяца = сумма расходов с occurred_on внутри месяца.
Результат месяца = доходы месяца - расходы месяца.
Остаток бюджета = лимит месяца - расходы месяца.
Процент использования = расходы месяца / лимит месяца × 100.
```

Доходы не увеличивают лимит автоматически. Для категории доля расходов считается относительно всех расходов месяца; при нулевых расходах показать пустое состояние, не делить на ноль. Баланс, результат месяца и остаток бюджета должны иметь разные подписи.

Для текущего месяца `оставшиеся дни = последний день месяца - сегодня + 1`. Дневной ориентир — `max(остаток бюджета, 0) / оставшиеся дни`, округлённый вниз до копейки. Например, 12 000 ₽ на 10 дней дают 1 200 ₽ в день. Это ориентир по лимиту, не обещание наличия денег на счёте. Для прошедших и будущих месяцев дневной ориентир отсутствует. Для процентов допускается округление только при отображении.

В MVP возврат записывается как доход и увеличивает баланс, но не уменьшает расходы бюджета. Такой эффект явно показывается в подсказке. Связанные возвраты с уменьшением исходного расхода — отдельная будущая функция.

## 5. Интерфейс и визуальные требования

### 5.1. Направление дизайна

Сдержанный современный интерфейс: свободное пространство, спокойный фон, аккуратные карточки, хорошая типографика и один основной акцентный цвет. Главное внимание — суммам, периоду и действию добавления операции. Не перегружать обзор графиками, декоративными градиентами и техническими терминами.

Создать единые дизайн-токены: цвета, отступы с базовой сеткой 4/8 px, радиусы, тени, размеры и веса шрифта, состояния элементов. Суммы выравнивать и показывать табличными цифрами. Использовать локально поставляемый шрифт с кириллицей и системный fallback.

Доход и расход различаются подписью и знаком, а не только зелёным/красным цветом. Основной размер текста около 16 px; второстепенный не меньше 14 px. Интерактивная область на телефоне — не меньше 44×44 px. Контраст основного текста — минимум 4,5:1; видимый фокус, доступные подписи и управление с клавиатуры обязательны.

Светлая, тёмная и системная темы; выбор сохраняется на устройстве. Анимации короткие, ориентир 120–200 мс, с поддержкой `prefers-reduced-motion`. Цвета категорий остаются различимыми в обеих темах.

### 5.2. Основные страницы

| Страница | Содержимое и действия |
| --- | --- |
| Обзор | Профиль, месяц, баланс за всё время, доходы/расходы месяца, бюджет, категории расходов, последние 5–10 операций |
| Операции | Группы по дням, сумма и категория, поиск по комментарию, фильтры дат/типа/категории, загрузка следующей страницы |
| Бюджет | Выбор месяца, установка/изменение лимита, расходы, остаток, прогресс и дневной ориентир |
| Категории | Разделы доходов/расходов, создание, изменение, архив и восстановление |
| Настройки | Имя профиля, начальный остаток и начало учёта, часовой пояс, тема, CSV-экспорт |

Редактор операции — диалог или боковая панель на компьютере и удобный нижний лист либо отдельный экран на телефоне. Клавиатура не закрывает сумму и кнопку сохранения; форма прокручивается.

На компьютере — боковая навигация и компактная верхняя панель. На телефоне — нижняя навигация для основных разделов и заметная кнопка добавления. Бюджет может быть доступен из обзора, категории и настройки — через «Ещё», чтобы не перегружать нижнюю панель.

Для расходов по категориям предпочтительны горизонтальные полосы с именами и суммами; диаграмма допустима как дополнение. Данные графика должны быть доступны текстом.

### 5.3. Состояния и проверка удобства

Обязательны: первоначальная загрузка, отсутствие профилей, отсутствие операций, пустой результат фильтра, бюджет не задан, перерасход, ошибка API, потеря сети, повторная попытка и успешное сохранение. При фильтрации не показывать «данных нет» до завершения запроса. Технические трассировки не выводить пользователю.

Проверить ширины 360, 390, 768, 1280 и 1920 px; горизонтальная прокрутка страницы отсутствует. На 360 px длинное имя категории, крупная сумма и длинный комментарий не ломают карточку. Сайт поддерживает масштабирование текста до 200%.

Основной сценарий добавления расхода выполняется без поиска по меню; целевой ориентир — не более 15 секунд для знакомого пользователя. Это проверяется вручную, а не считается гарантией по числу кликов.

### 6.1. Предлагаемый стек

| Слой | Предложение | Основание выбора |

Использовать стабильные поддерживаемые версии, совместимость которых проверена при старте реализации. Зафиксировать зависимости и lock-файлы; не применять `latest` для воспроизводимых серверных образов. Точные версии выбираются при реализации, а не угадываются в этом документе.

### 6.2. Границы модулей

```text
Браузер ── HTTPS ── Caddy
                       ├── статические файлы сайта
                       └── /api/* → API → PostgreSQL

Позже: Rust-клиент / мобильный клиент → тот же API
Позже: адаптер импорта → черновики → подтверждение → сервис операций
```

Backend — один модульный сервис. Отделить HTTP-схемы и маршруты, прикладные операции, правила денег/бюджета и хранение. Бизнес-правила не размещать в компонентах UI и не дублировать в каждом будущем клиенте. Сервер является источником истины для финансовых показателей.

Не нужны микросервисы, брокер сообщений, Redis, Kubernetes, event sourcing или универсальная система плагинов. Фоновый worker добавляется только при появлении реального импорта, а не заранее.

Предлагаемая структура после начала реализации:

```text

backend/              API, финансовые правила, миграции, тесты
infra/                Dockerfile, Compose, настройки прокси и backup
api/                  экспортированный openapi.json, примеры запросов

README.md             запуск, обновление и восстановление

```

В рамках текущей задачи создаётся только этот документ; перечисленные каталоги — будущая структура.

## 7. Модель данных и целостность

Идентификаторы сущностей — UUID. Все финансовые сущности принадлежат профилю. Физическая модель ниже относится к MVP; полноценные сущности банков и счетов пока не добавляются.

| Сущность | Основные поля |
| --- | --- |
| Profile | `id`, `name`, `timezone`, `currency=RUB`, `created_at`, `updated_at` |
| Wallet | `id`, `profile_id` UNIQUE, `name`, `opening_balance_minor`, `tracking_start_date`, `version`, технические времена |
| Category | `id`, `profile_id`, `type=income/expense`, `name`, нормализованное имя, `icon`, `color`, `is_archived`, технические времена |
| Transaction | `id`, `profile_id`, `wallet_id`, `category_id`, `type`, `amount_minor`, `occurred_on`, `note`, `source=manual`, `version`, `deleted_at`, технические времена |
| MonthlyBudget | `id`, `profile_id`, `month` (первый день месяца), `limit_minor`, `version`, `deleted_at`, технические времена; UNIQUE `(profile_id, month)` |
| CategoryBudget | `id`, `profile_id`, `category_id`, `category_type=expense`, `month`, `limit_minor`, `version`, `deleted_at`, технические времена; UNIQUE `(profile_id, month, category_id)`; составной FK к расходной категории своего профиля |

`source` в MVP допускает только `manual`; новые значения появляются с соответствующей миграцией и версией контракта. Сырые банковские сообщения и файлы не хранятся в таблице операций.

Обязательные ограничения:

- Тип операции совпадает с типом категории; категория и кошелёк принадлежат тому же профилю.
- Связи между профилями блокируются серверной проверкой и составными внешними ключами там, где это применимо. UUID сам по себе не подтверждает принадлежность.
- Сумма операции и лимит положительные, начальный остаток может быть отрицательным.
- Начальная и операционная даты проверяются в одной транзакции с изменением данных, чтобы параллельные запросы не нарушали период учёта.
- Уникальность категорий учитывает также архивные записи; повторное имя предлагает восстановить существующую категорию.
- Для операций индекс `(profile_id, occurred_on DESC, id DESC)`; по необходимости индексы фильтров категории/типа после измерений.
- Для budgets индекс уникальности профиля и месяца. Денежные агрегаты считают только неудалённые операции.
- Для лимитов категорий уникальность включает профиль, месяц и категорию, в том числе удалённые служебные записи. Показатели категорий в обзоре используют тот же согласованный снимок БД, что и общий бюджет.

Сохранять операцию и проверять её ссылки атомарно. Параллельное архивирование категории и добавление операции не должно обходить правила. Использовать транзакции и подходящие блокировки/условные изменения в PostgreSQL.

Баланс и статистику рассчитывать из исходных записей запросами БД. Отдельная изменяемая таблица итогового баланса в MVP не нужна. Показатели одного ответа обзора получать из согласованного снимка данных, чтобы расход не учитывался только в части карточек.

Миграции обязательны. Автоматическое удаление БД при несовпадении схемы запрещено. Проверять обновление на копии данных предыдущей версии.

## 8. Контракт API первого релиза

### 8.1. Общие правила

Базовый путь: `/api/v1`. JSON UTF-8; URL и поля на английском, пользовательские сообщения на русском. Денежные строки — по разделу 4; даты — `YYYY-MM-DD`, месяцы — `YYYY-MM`, технические времена — ISO 8601 UTC. Неизвестные входные поля отклонять.

Для профильных ресурсов путь начинается с `/profiles/{profile_id}`. Сервер фильтрует по профилю каждый запрос, включая получение по ID, экспорт и агрегаты. Обращение к сущности другого профиля возвращает `404`.

Успешное создание — `201` с сущностью и `Location`; получение и изменение — `200`; успешное удаление — `204` без JSON-тела. Нет скрытых побочных изменений других профилей.

В MVP профили не требуют токена или пароля. Для сайта и API используется один origin. В development разрешить только явные адреса frontend; не включать глобальный CORS `*`. Общий контроль входа на сервер при необходимости описан в разделе 10.

### 8.2. Маршруты

Все пути ниже, кроме health checks, указаны относительно `/api/v1`.

| Метод и путь | Назначение / данные |
| --- | --- |
| `GET /profiles` | Список профилей: `items` |
| `POST /profiles` | Создать профиль: `id` (UUID клиента), `name`, необязательный `timezone`; кошелёк и категории создаются автоматически |
| `GET /profiles/{p}` | Профиль |
| `PATCH /profiles/{p}` | Имя и/или часовой пояс |
| `GET /profiles/{p}/wallet` | Общий кошелёк, начальный остаток, начало учёта и `version` |
| `PATCH /profiles/{p}/wallet` | Начальный остаток/дата начала и обязательная текущая `version` |
| `GET /profiles/{p}/categories` | Категории; `type`, `include_archived` (по умолчанию false) |
| `POST /profiles/{p}/categories` | `id`, `name`, `type`, `icon`, `color` |
| `PATCH /profiles/{p}/categories/{id}` | Имя, значок, цвет и/или `is_archived`; тип неизменяем |
| `GET /profiles/{p}/transactions` | История с фильтрами и курсором |
| `POST /profiles/{p}/transactions` | Создать ручную операцию с UUID клиента |
| `GET /profiles/{p}/transactions/{id}` | Одна неудалённая операция |
| `PATCH /profiles/{p}/transactions/{id}` | Изменение полей операции и обязательная текущая `version` |
| `DELETE /profiles/{p}/transactions/{id}?version=N` | Пометить удалённой с проверкой версии |
| `GET /profiles/{p}/summary?month=YYYY-MM` | Баланс, доходы/расходы, результат, категории, бюджет и дневной ориентир |
| `GET /profiles/{p}/budgets/{month}` | Бюджет месяца либо `404`, если он не задан |
| `GET /profiles/{p}/category-budgets/{month}` | Расходные категории с лимитами/расходами, сумма лимитов и предупреждение превышения общего бюджета |
| `PUT /profiles/{p}/category-budgets/{month}/{id}` | `id` категории: создать лимит без `version` или изменить с текущей `version` |
| `DELETE /profiles/{p}/category-budgets/{month}/{id}?version=N` | Удалить лимит категории, сохранив операции и историю версий |
| `PUT /profiles/{p}/budgets/{month}` | Создать/заменить лимит; для обновления обязательна текущая `version` |
| `DELETE /profiles/{p}/budgets/{month}?version=N` | Удалить лимит; операции сохраняются |
| `GET /profiles/{p}/exports/transactions.csv` | CSV неудалённых операций; `date_from`, `date_to`, `type`, `category_id`, `q` |
| `GET /health/live` | Процесс работает; без доступа к БД |
| `GET /health/ready` | API готово, схема актуальна, БД доступна; `503` при неготовности |

`/health/*` находится в корне сервера, а не под `/api/v1`. Прокси должен передавать эти пути в API. Состояние профиля в браузере не является серверной сессией; выбранный UUID передаётся явно в пути.

### 8.3. История, пагинация и экспорт

Фильтры: `date_from` включительно, `date_to` исключительно, `type`, `category_id`, `q` по подстроке комментария без учёта регистра. `q` — максимум 100 символов, литералы `%` и `_` не становятся SQL-масками. Некорректный период — `422`.

Сортировка стабильная: `occurred_on DESC, id DESC`. `limit` по умолчанию 50, максимум 200. Курсор непрозрачный, связан с профилем и фильтрами; изменение фильтров начинает новую выдачу. Неверный курсор — `400`. Ответ:

```json
{
  "items": [],
  "next_cursor": null,
  "has_more": false
}
```

`next_cursor` и `has_more` согласованы. Дорогой общий `count` для каждой страницы не обязателен. После создания, изменения или удаления сайт обновляет кеш и начинает выдачу заново. Курсор не обещает неизменный снимок истории при параллельном редактировании.

CSV-экспорт использует те же фильтры, но выгружает весь результат без параметров пагинации, потоково. UTF-8 с BOM для открытия в Excel; разделитель `;`, кавычки и переводы строк экранируются. Колонки: ID, профиль, тип, дата, категория, сумма в рублях с запятой, валюта, комментарий, источник. Текстовые поля с формульными префиксами `=`, `+`, `-`, `@` экспортировать как безопасный текст. CSV не является полной резервной копией БД.

### 8.4. Создание операции и повторные запросы

Запрос `POST /api/v1/profiles/{profile_id}/transactions`:

```json
{
  "id": "519bcf15-7ffb-4de7-9db7-1dcc77d312fe",
  "type": "expense",
  "amount_minor": "125050",
  "category_id": "2d0b4db1-29a6-48aa-8a8c-a77b978a9d52",
  "occurred_on": "2026-10-13",
  "note": "Продукты на неделю"
}
```

Обязательны все поля, кроме `note` (по умолчанию пустая строка). `wallet_id` сервер берёт из профиля. Ответ `201` содержит эти поля, `profile_id`, `wallet_id`, `source: "manual"`, `version: 1`, `created_at` и `updated_at`.

Клиент создаёт UUID один раз до отправки и сохраняет при повторе после таймаута. Повтор `POST` с тем же ID и теми же текущими значениями возвращает существующую запись с `200` без дубля. Тот же ID с другим содержимым — `409 duplicate_id`; после изменения записи повтор устаревшего содержимого также даёт `409`. Для удалённой операции повтор `POST` возвращает `410`, не восстанавливая запись. Уникальность проверяется в БД, включая одновременные запросы. При совпадении ID с ресурсом другого профиля — `409` без раскрытия чужих данных.

Для создания профиля и категории также передавать UUID клиента: одинаковый повтор не создаёт новые сущности, несовпадение содержимого даёт `409`. Вспомогательные сущности профиля создаются один раз в общей транзакции.

Изменение операций, кошелька и бюджета увеличивает `version`. Устаревшая версия — `409 stale_version`; сайт предлагает перезагрузить запись. Для `PUT` бюджета без `version` допускается только создание отсутствующего лимита. Уже существующий лимит без версии даёт `409`; повтор после потери ответа разрешается получением актуального бюджета. Удаление бюджета также увеличивает версию и сохраняет служебную запись; повторное создание продолжает нумерацию, поэтому старая вкладка не перезаписывает новый лимит. В UI, GET и статистике удалённого лимита нет. Удаление требует версию; повтор удаления уже удалённой операции или бюджета возвращает `204`. Обновление удалённой операции — `404`.

### 8.5. Обзор

`summary` содержит `month`, `currency`, `balance_minor`, `income_minor`, `expense_minor`, `net_minor`, массив категорий с суммами расходов и объект `budget` либо `null`.

Если бюджет задан, объект включает `limit_minor`, `spent_minor`, `remaining_minor`, `used_percent` (десятичная строка, например `"62.5"`), `daily_available_minor` и `days_remaining`. Последние два поля равны `null` вне текущего месяца. При перерасходе `remaining_minor` отрицательный, дневной ориентир равен `"0"`. Месяц без операций возвращает нулевые строковые суммы; баланс за всё время остаётся независимым от выбранного месяца.

### 8.6. Ошибки

```json
{
  "error": {
    "code": "validation_error",
    "message": "Сумма должна быть больше нуля",
    "fields": {"amount_minor": "Минимальная сумма — 1 копейка"},
    "request_id": "req_01"
  }
}
```

| Статус | Смысл |
| --- | --- |
| `400` | Некорректный JSON или курсор |
| `404` | Профиль/ресурс не найден либо не принадлежит указанному профилю |
| `409` | Конфликт версии, имени, ID, даты начала учёта или состояния категории |
| `410` | Попытка повторно создать удалённую операцию с тем же ID |
| `422` | Ошибка поля, суммы, даты, типа категории или параметра |
| `500` | Неожиданная ошибка; без внутренних подробностей |
| `503` | Временная неготовность сервиса/БД |

Сайт разбирает `code` и `fields`, а не текст сообщения. Сетевые ошибки обрабатываются отдельно. GET можно повторять с ограниченным backoff; POST повторяется с тем же UUID. Конфликты и ошибки валидации не повторять автоматически. Не считать таймаут доказательством того, что запись не сохранена.

### 8.7. Документация API

Машинный контракт хранится в `api/openapi.json` и является источником типов клиента. Go API должен соответствовать этому контракту. Изменения интерфейса сначала отражаются в требованиях и OpenAPI, затем в Go-обработчиках, клиентах и проверках.

OpenAPI описывает все параметры, денежные строки, обязательность/nullability, примеры, статусы и конфликты. Типизированный web-клиент генерируется из него. Совместимые новые поля допускаются внутри `v1`; удаление поля, изменение денежного формата или смысла расчёта требуют нового контракта и плана миграции клиентов.

Для проверки сохранить небольшую Postman-коллекцию, сгенерированную из OpenAPI и дополненную assertions: создание профиля, дохода и расхода, повтор POST, summary, бюджет, чужая категория, изменение, удаление. `base_url` задаётся окружением. Postman CLI установлен; привязка к облачному workspace и публикация документации в MVP не нужны. Не хранить вторую вручную поддерживаемую спецификацию, расходящуюся с OpenAPI.

## 9. Надёжность и производительность

В MVP предусмотреть до 5 профилей и 100 000 операций на профиль. Это тестовый объём, не повод заранее усложнять архитектуру.

На сервере с 2 vCPU и 2 GB RAM после прогрева целевые показатели: p95 получения страницы истории и обзора до 300 мс; сохранения операции до 500 мс. Проверка — с БД указанного объёма и до 5 одновременных клиентов, без учёта внешней сети. Это цели, которые нужно измерить; текущая задача не подтверждает их достижение.

Сайт должен показывать первый пригодный к действию экран примерно за 2 секунды в обычной сети; целевой LCP до 2,5 секунды на согласованном мобильном профиле проверки. Не загружать всю историю в браузер для расчёта бюджета. Поиск запускается с короткой задержкой; предыдущие запросы отменяются либо их устаревшие ответы игнорируются.

Ошибки записи не теряют форму. После успешного ответа данные сохраняются в БД и переживают перезапуск контейнеров. Автоматическое повторение запросов ограничено. Предусмотреть graceful shutdown сервера и ограниченные таймауты запросов/БД. Если БД недоступна, операции не записываются в память как будто сохранённые.

## 10. Развёртывание и минимальная защита

### 10.1. Топология

Предполагается собственный Linux-сервер с Docker и Compose, доступным диском и доменом либо приватным адресом. Неизвестные сейчас параметры сервера уточняются перед развёртыванием; не требуется настраивать сервер в текущей задаче.

Три основных сервиса: прокси/статический frontend, API, PostgreSQL. Только прокси публикует сетевые порты. БД и API доступны внутри Compose-сети; данные PostgreSQL хранятся в постоянном томе. Настроить health checks, перезапуск и ограничение роста логов. Для публичного домена использовать HTTPS и автоматическое продление сертификата.

Сайт и API обслуживаются с одного origin: frontend `/`, API `/api/v1/*`. Прокси отдельно обрабатывает API/health и fallback клиентской маршрутизации; неизвестный API-путь не возвращает HTML сайта с `200`.

### 10.2. Доступ

По пожеланию владельца внутри приложения нет регистрации, паролей профиля, JWT, OAuth, ролей и 2FA. На приватной сети/VPN сайт может работать без входа вообще. Если тот же режим открыть всему интернету, любой посетитель сможет видеть и изменять все профили.

Для публичного размещения предлагается необязательный общий пароль на весь сайт на уровне прокси; он не меняет сценарий «создать профиль по имени». Альтернатива — доступ через VPN. Конкретный режим выбирается при развёртывании, а не навязывается реализации профилей. При использовании общего входа будущие клиенты должны получить совместимый способ доступа к API; это проверяется до их выпуска.

Базовые инженерные требования сохраняются в любом режиме: валидация, параметризованные SQL-запросы, вывод пользовательского текста без исполнения HTML, отсутствие секретов в Git и финансовых содержимых в логах. Не подключать аналитику, рекламу или внешнюю телеметрию по умолчанию. Загружаемые банковские файлы в будущем не передавать сторонним AI-сервисам без отдельного решения владельца.

### 10.3. Конфигурация и выпуск

Будущий `.env.example` описывает `DATABASE_URL`, домен/origin, режим окружения, уровень логов и настройки резервирования; реальные значения — вне Git. Ключи общего входа, если он выбран, также остаются вне репозитория. API использует БД-пользователя приложения; административные учётные данные не встроены в frontend.

Процедура первого запуска: заполнить конфигурацию → запустить БД → выполнить миграции отдельной командой → запустить API и прокси → проверить readiness → открыть сайт и создать профиль. Не запускать миграции конкурентно из каждого worker.

Обновление: сделать backup → получить зафиксированную версию → выполнить миграции → обновить контейнеры → проверить readiness и контрольный сценарий. Откат образа возможен только при совместимости схемы; иначе нужны предусмотренная обратная миграция или восстановление backup с понятной потерей более новых данных.

### 10.4. Backup и журналирование

Делать автоматический ежедневный `pg_dump` в согласованном формате. Хранить как минимум 7 последних дневных и 4 недельных копии; хотя бы одну копию — вне диска основного сервера. При нехватке диска/ошибке резервирования сохранять явный статус и сообщать владельцу выбранным при настройке способом.

Цель: потеря не более 24 часов данных при восстановлении последней успешной копии; восстановление до часа на доступном сервере. Проверить это реальным восстановлением в отдельную БД, а не только наличием файла backup. Перед миграциями создавать дополнительную копию. Не использовать `docker compose down -v` при обычном обновлении.

Логи содержат время, уровень, маршрут, статус, длительность, код ошибки и `request_id`; без комментариев операций, денежных тел запросов, банковских сообщений и секретов. Финансовые данные находятся в БД и backup, а не в журнале HTTP. В MVP достаточно структурированных логов и health checks, без отдельной платформы наблюдаемости.

## 11. Будущая автоматизация

### 11.1. Ожидаемый результат

Под автоматическим учётом понимается получение операций, определение суммы/даты/типа и предложенной категории, затем пересчёт баланса и бюджета. Приложение не может гарантировать актуальный банковский остаток по неполному набору уведомлений: начальный остаток и полнота импорта всё равно требуют сверки.

Общий поток:

```text
Источник → извлечение → нормализация → проверка дублей
         → черновик операции → проверка пользователем → запись → пересчёт
```

В первой версии импорта операции создаются после подтверждения. Автоподтверждение можно добавить только для проверенного источника с измеренной точностью, журналом результата и возможностью исправления.

### 11.2. Рекомендуемый порядок

| Этап | Источник | Почему и ограничения |
| --- | --- | --- |
| 1 | CSV/XLSX выписка конкретного банка | Структурированные строки, понятный период и возможность сверки; формат выбирается по реальному обезличенному примеру |
| 2 | Текстовая PDF-выписка | Извлечение таблиц; сканированная PDF требует OCR и другого уровня проверки |
| 3 | Скриншоты / OCR | Ошибки цифр, даты, знака и валюты; обязательное редактирование распознанного результата |
| 4 | Android-уведомления | Нужен установленный клиент/сборщик, системный доступ и обработка неполных/повторных событий |

Это предложение по порядку, а не обещание поддержки любого банка. Для каждого адаптера нужны реальные образцы, примеры возвратов, переводов, отказов, комиссий и дублей. Сначала поддержать один подтверждённый формат.

### 11.3. Ограничения уведомлений

Обычный сайт не читает уведомления других приложений на Android. Будущий Android-клиент может использовать `NotificationListenerService` с отдельно включённым пользователем системным доступом. Обычное разрешение показывать уведомления не даёт права читать банковские.

Системные ограничения, скрытый текст и отключение фонового сервиса могут приводить к пропускам. Обновление одного уведомления не всегда означает новую операцию. Уведомления о неуспешной оплате, кодах и служебных событиях не должны становиться расходами. Необходимы allowlist выбранных приложений, дедупликация, ограниченная локальная очередь и повторная отправка с тем же ID после восстановления сети.

Для будущего Rust/Tauri-клиента системное чтение Android-уведомлений потребует нативной интеграции; одного web-интерфейса или Rust-кода общего API недостаточно. Выбор мобильной технологии проверяется на устройстве до обязательства использовать её для этой функции. Поддержка iOS-уведомлений других приложений не обещается.

### 11.4. Данные импорта и дубли

Позже добавить отдельные сущности `ImportBatch`, `ImportItem`, `SourceAdapter`, при необходимости `SourceDocument`. Черновик хранит источник, внешний ID (если есть), исходную дату/часовой пояс, распознанные поля, предупреждения, версию парсера и статус подтверждения.

Вначале использовать надёжный внешний идентификатор. Хеш суммы/даты/описания — признак возможного дубля, но не основание автоматически удалить две одинаковые реальные покупки. Повторная выписка, push и скриншот одной операции должны сопоставляться с уже существующей записью, включая ручную, через проверяемую процедуру.

Импорт пакетный, с предпросмотром: какие строки будут добавлены, пропущены или требуют проверки. Повторное подтверждение пакета не создаёт новые записи; частичный сбой показывает результаты по строкам. Переводы между собственными счетами не считать доходом/расходом; пока нет модели нескольких счетов, такие строки помечать для ручной проверки или пропускать с объяснением.

Сырьё импортов сохраняется только при необходимости с ограниченным сроком и возможностью удаления. Выбор OCR/AI-библиотек, ограничения файлов, политика хранения и схема будущего API импорта описываются отдельным ТЗ после проверки образцов. Эти сущности и маршруты в MVP реализовывать не требуется.

## 12. Будущие клиенты

Rust-приложение рассматривается как отдельный клиент API, преимущественно настольный; конкретную целевую платформу нужно подтвердить перед его началом. Предложение: Tauri для повторного использования web-интерфейса и Rust для системных функций. Полностью нативный Rust UI также возможен без изменения финансового API.

Мобильное приложение использует тот же сервер и профили. Сначала обеспечить ручной учёт, затем чтение уведомлений. Не переносить единственную копию данных с сервера на устройство и не дублировать формулы бюджета в нескольких независимых реализациях.

Офлайн-режим позже требует отдельного контракта: устойчивой очереди команд, идентификаторов, версий, правил конфликтов и удаления. Текущий MVP поддерживает повтор запросов, но не заявляет полноценную офлайн-синхронизацию.

## 13. Проверки и критерии готовности MVP

### 13.1. Обязательные автоматические проверки при реализации

- Деньги: 0,01 ₽, максимальная сумма, запятая/точка, лишние дробные знаки, отрицательные значения, точные большие агрегаты и формат денежных JSON-строк.
- Расчёты: начальный остаток не считается доходом, доход/расход, отрицательный баланс, изменение и удаление, пустой месяц, перерасход, последний день месяца, високосный февраль и дневной ориентир.
- API и настоящая PostgreSQL: CRUD, принадлежность профилю, ограничения категорий, архив, неверные даты, курсоры, повторные и конкурентные POST, устаревшие версии, ошибки бюджета и целостность транзакций.
- Миграции и восстановление: данные предыдущей схемы остаются доступными; backup действительно восстанавливается.
- CSV: полный результат фильтра, кириллица, кавычки, переносы строк, сумма без округления и безопасные текстовые ячейки.
- Web E2E: создать профиль → задать остаток → добавить доход и расход → изменить расход → установить бюджет → проверить показатели → удалить запись → перезагрузить страницу.
- Смена профиля: данные не смешиваются, в том числе при задержанных сетевых ответах.

Не требовать искусственного процента покрытия. Проверять наблюдаемое поведение и риски расчётов, а не детали внутренней реализации. Postman-коллекция дополняет, а не заменяет unit/integration/E2E-проверки.

### 13.2. Контрольные примеры

Для профиля с начальным остатком 10 000 ₽: доход 30 000 ₽ и расход 1 250,50 ₽ дают баланс 38 749,50 ₽. Месячный лимит 20 000 ₽ даёт остаток 18 749,50 ₽. После изменения расхода на 1 000 ₽ баланс равен 39 000 ₽, остаток бюджета — 19 000 ₽. После удаления расхода — 40 000 ₽ и 20 000 ₽ соответственно. Другой профиль остаётся без изменений.

При лимите 5 000 ₽ и расходах 6 000 ₽: остаток −1 000 ₽, использование 120%, дневной ориентир текущего месяца 0 ₽. При отсутствии лимита остаток/процент не показываются. Выбор другого месяца меняет месячные показатели, но не баланс за весь период.

### 13.3. Релиз готов, когда

1. Все функции из раздела 2.1 работают на собственном сервере владельца.
2. Финансовые контрольные примеры и обязательные проверки проходят.
3. Данные переживают перезапуск, миграция и восстановление backup проверены.
4. Интерфейс проверен на указанных ширинах, в обеих темах, с клавиатурой и на реальном телефоне.
5. Ошибки сети/валидации не теряют форму и не создают дубли.
6. OpenAPI, клиент и примеры запросов согласованы; будущий клиент может пользоваться API без знания внутренних таблиц.
7. Измерены целевые показатели производительности; отклонения явно описаны.
8. Есть README с запуском, конфигурацией, обновлением, backup/restore и выбранным режимом доступа.

Эти критерии используются при проверке реализации MVP. Фактически выполненные проверки и ограничения окружения фиксируются в VERIFICATION.md.

## 14. Порядок реализации

1. Уточнить платформу сервера и режим доступа; утвердить стек и компактный макет обзора/редактора для телефона и компьютера.
2. Создать API, миграции, профили, кошелёк, категории и операции; сразу проверить точность денег и принадлежность данных.
3. Реализовать сайт: профили, обзор, редактор и история на реальном API.
4. Добавить месячный бюджет, темы, пустые состояния и CSV-экспорт.
5. Подготовить Compose, backup/restore, документацию API и завершить E2E/адаптивную проверку.
6. Развернуть и пользоваться ручным трекером; по реальным затруднениям уточнить следующий релиз.
7. Отдельно исследовать одну банковскую выписку и выпустить импорт с подтверждением; затем рассматривать OCR, Rust-клиент и Android-уведомления.

Не начинать седьмой шаг до готовности ручного учёта и его резервного копирования. Автоматизация не должна задерживать первую полезную версию.

## 15. Предположения и решения перед следующими этапами

Решения, принятые владельцем: серверная часть на Go, развёртывание на собственном сервере. До развёртывания и следующих этапов уточнить:

- Linux-дистрибутив, архитектуру CPU, объём RAM/диска, наличие Docker и домена.
- Приватный доступ/VPN, общий пароль на прокси или сознательно открытый сайт без входа.
- Принять один кошелёк и RUB на MVP либо изменить границы первого релиза до разработки.
- Целевую платформу Rust-приложения и приоритет Android/iOS — перед клиентскими этапами.
- Банк и доступный формат обезличенной выписки — перед первым импортом.

Все текущие допущения выбраны для минимального рабочего продукта. Дополнительные возможности требуют отдельного решения о расширении объёма, а не скрытого включения в MVP.
