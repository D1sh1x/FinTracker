# ФинТрек

**Статус: альфа-версия развёрнута на VPS.** С телефона и ПК: **https://167.86.68.233:9443** с общим входом. Логин `owner`, пароль — в локальном `.local/vps-access.txt`. Работают личный учёт, бюджеты категорий, импорт скриншотов и капитал. Инструкция: [docs/VPS_DEPLOYMENT.md](docs/VPS_DEPLOYMENT.md). Android APK: [docs/ANDROID.md](docs/ANDROID.md). Приватный SSH-доступ через `http://127.0.0.1:18088` сохранён. Qwen на VPS пока не запущен.

Адаптивный сайт для личных финансов: профили по имени, доходы/расходы, категории, история, общий месячный бюджет, лимиты категорий и CSV. Серверная часть — **Go**, база — PostgreSQL, интерфейс — React + TypeScript. Python для приложения не нужен.

Технические требования: [REQUIREMENTS.md](REQUIREMENTS.md). Проверки и ограничения: [VERIFICATION.md](VERIFICATION.md).

**Капитал:** [http://localhost:8088/#capital](http://localhost:8088/#capital). Добавляйте обычные и накопительные счета, вклады и инвестиционный портфель. Переводы не являются расходами, переоценка не меняет бюджеты. История и правила расчётов: [docs/CAPITAL.md](docs/CAPITAL.md).

**Импорт скриншотов встроен в основной сайт:** [http://localhost:8088/#imports](http://localhost:8088/#imports). Файл или Ctrl+V → распознавание → правки → подтверждение выбранных строк. Неизвестные категории — «Не определено». Запуск модели, правила повторов и хранение данных: [docs/SCREENSHOT_IMPORT.md](docs/SCREENSHOT_IMPORT.md).

Локальная лаборатория скриншотов и Qwen3-4B: http://localhost:8090. Можно выбрать PNG/JPEG или вставить скриншот через Ctrl+V. Запуск и измерения CPU/GPU описаны в [docs/LOCAL_IMPORT_TEST.md](docs/LOCAL_IMPORT_TEST.md). Она показывает предпросмотр и категории, включая «Не определено»; финансовые операции при тесте не создаются.

## Быстрый запуск в Docker

Нужны Docker с запущенным движком и Docker Compose. Node.js и Go на сервере не требуются: сборка выполняется внутри контейнеров. Образы зафиксированы по digest, зависимости — в go.sum и package-lock.json.

1. Скопируйте `.env.example` в `.env`, если файл ещё не существует.
2. Задайте `POSTGRES_PASSWORD`: длинную случайную строку из латинских букв/цифр, подходящую для URL. Не меняйте пароль уже созданной БД просто редактированием `.env`: сначала измените его в PostgreSQL.
3. Запустите:

```sh
docker compose up -d --build --wait
```

На Windows в папке с кириллицей используйте:

```powershell
.\scripts\compose.ps1
```

Скрипт временно использует свободную букву диска только для сборки, затем убирает алиас. Контейнеры и backup-mounts привязаны к настоящей папке. Это обходит ошибку BuildKit `non-printable ASCII characters` в пути проекта.

Откройте **http://127.0.0.1:8088**, создайте профиль и начните учёт. В подготовленном локальном окружении `.env` уже создан со случайным паролем БД; он исключён из Git. Тестовые профили находятся в отдельных базах и не появляются в приложении.

Сервисы: `db` → одноразовый `migrate` → `api` → `frontend`; `backup` делает копии базы. Завершившийся с кодом 0 контейнер `migrate` — нормальное состояние. БД и API не публикуют порты наружу. При обычном перезапуске данные остаются в томе `fintrack_database`.

```sh
docker compose ps
docker compose logs --tail=100 api
docker compose restart api frontend
docker compose down
```

Не добавляйте `-v` к `down` при обычной остановке: это удалит тома данных.

## Собственный сервер

Для существующего VPS с нодами/VPN используйте отдельную [инструкцию развёртывания](docs/VPS_DEPLOYMENT.md) и `compose.vps.yml`: он оставляет 443/8443 существующим сервисам. Описанный ниже общий вариант с публичными 80/443 подходит для сервера со свободными портами.

Для Linux скопируйте исходники, создайте `.env` и выполните команду Docker выше. Для публичного домена:

```dotenv
SITE_ADDRESS=finance.example.com
HTTP_BIND=0.0.0.0
HTTP_PORT=80
HTTPS_PORT=443
```

Заранее направьте DNS на сервер и откройте 80/443. Caddy выдаст и будет продлевать HTTPS-сертификат. Для приватной сети оставьте доступ через VPN/локальный адрес; при необходимости измените `HTTP_BIND` на адрес нужного интерфейса.

У профилей нет индивидуальной авторизации. На публичном адресе без общего входа все профили доступны любому посетителю. Необязательный пароль на весь сайт:

1. Получите хеш командой `docker compose exec frontend caddy hash-password` и введите пароль в интерактивный запрос.
2. Сохраните хеш в `.env` как `BASIC_AUTH_HASH='полученный-хеш'` — в одинарных кавычках, чтобы `$` не интерполировались.
3. Запускайте с override:

```sh
docker compose -f compose.yml -f compose.auth.yml up -d --build --wait
```

Общий вход применяется и к API через прокси. Внутренние health checks работают без него. Для будущего Rust/мобильного клиента потребуется отправлять тот же общий Basic Auth, если выбран этот режим.

## Резервные копии и восстановление

`backup` выполняет `pg_dump -Fc` при запуске и каждые 24 часа. В `backups/` сохраняются 7 дневных и 4 недельных копии; последняя копия текущей недели обновляется. `last-success` содержит UTC-время успешной копии, `last-error` появляется при ошибке. Health check становится unhealthy при ошибке или отсутствии свежего успеха более 26 часов.

Вне основного диска/сервера нужно отдельно настроить копирование каталога `backups/`. Отправка уведомлений не подключена: для неё выберите механизм мониторинга при настройке своего сервера. Не включайте `.env`, backups и финансовые файлы в Git.

Принудительно сделать копию:

```sh
docker compose exec backup /bin/sh /scripts/backup.sh
```

Проверить восстановление в **новую**, ранее не существующую тестовую БД:

```sh
docker compose cp backups/daily-YYYY-MM-DD.dump db:/tmp/restore.dump
docker compose exec db createdb -U fintrack fintrack_restore_test
docker compose exec db pg_restore -U fintrack -d fintrack_restore_test --exit-on-error /tmp/restore.dump
docker compose exec db psql -U fintrack -d fintrack_restore_test -c 'SELECT count(*) FROM transactions;'
```

Если тестовая БД уже существует, выберите другое имя. Рабочая БД называется `fintrack_go`; эти команды её не изменяют. Для восстановления рабочего приложения остановите API и backup, сохраните копию текущей БД, восстановите dump в новую БД, переключите `DATABASE_URL` у API/migrate и `PGDATABASE` у backup в Compose и затем запускайте сервисы. Сохраните старую БД до проверки результата. Новые записи, сделанные после выбранной копии, в восстановленной базе отсутствуют.

## Обновление

Сделайте свежую копию, обновите исходники и запустите `docker compose up -d --build --wait`. Миграция выполняется отдельным сервисом и защищена транзакцией и advisory lock. Проверьте `/health/ready` и контрольную операцию. На Windows используйте `scripts/compose.ps1`.

SQL-миграции находятся в `backend/internal/store/`; текущая версия — `0003`. Миграция `0002` сохраняет удалённые общие бюджеты как служебные записи, а `0003` добавляет лимиты категорий с тем же правилом версий, не изменяя существующие операции. При следующем изменении схемы добавляйте новую миграцию в список `Migrate` и обновляйте `CurrentVersion`; не переписывайте применённые SQL-файлы. Откат образа безопасен только при совместимой схеме. Если схема несовместима, используйте подготовленную обратную миграцию либо проверенный backup.

## Разработка без сборки контейнеров приложения

Нужны Go 1.26+ и Node.js 24+. PostgreSQL можно запустить отдельно:

```sh
docker compose -f infra/compose.dev.yml up -d --wait
cd backend
go run ./cmd/fintrack migrate
go run ./cmd/fintrack
```

В другом терминале:

```sh
cd frontend
npm ci
npm run dev
```

Сайт: http://127.0.0.1:5173; API: http://127.0.0.1:8000. Vite передаёт `/api` в Go API с того же origin. В development БД `fintrack_go`, пользователь/пароль `fintrack` на `127.0.0.1:5432`; эти значения относятся только к `infra/compose.dev.yml`. Production использует отдельный закрытый контейнер и пароль из `.env`.

`DATABASE_URL`, `LISTEN_ADDR`, `OPENAPI_PATH` читаются из окружения Go-процесса. Backend не загружает `.env` автоматически; Compose подставляет значения самостоятельно. Локальный dev-сервер по умолчанию слушает только loopback.

## Проверки

Для Go-тестов создайте отдельную базу **один раз**:

```sh
docker compose -f infra/compose.dev.yml exec db createdb -U fintrack fintrack_test
cd backend
go test ./...
go vet ./...
go test -race ./...
```

Каждый integration test создаёт свою случайную схему и удаляет только её. Пользовательская БД не очищается. `TEST_DATABASE_URL` позволяет изменить адрес тестовой базы; её имя должно заканчиваться на `_test`. Race detector на Windows требует C-компилятора; в этом проекте он проверен в Linux-контейнере Go с PostgreSQL.

```sh
cd frontend
npm test
npm run build
npx playwright install chromium
```

Для E2E один раз создайте `fintrack_e2e_test` в development PostgreSQL и примените туда Go-миграцию с `DATABASE_URL`, указывающим на неё. Затем `npm run test:e2e` из `frontend/`: Playwright сам поднимает тестовый API на 8001 и сайт на 5174, а после проверки останавливает их. Тестовые данные не попадают в обычное приложение. Скриншоты проверки сохраняются в `.local/screenshots/` и не коммитятся.

## API и Postman

На странице «Бюджет» доступны общий лимит и блок «Бюджеты категорий». Нажмите «Задать лимит» у расходной категории: например, 5 000 ₽ на кафе или 40 000 ₽ на дом. Для каждого месяца лимиты независимы. Категории без лимита показывают фактические расходы без процента использования; заданные лимиты показывают остаток, прогресс и перерасход. В обзоре отображаются до трёх заданных лимитов и ссылка на остальные.

Лимиты категорий работают без общего бюджета и не изменяют его. Если их сумма превышает общий лимит, сайт показывает предупреждение. Доходы не увеличивают лимиты. После изменения суммы, даты, категории или удаления операции оба уровня пересчитываются на сервере. Архивная категория сохраняет свои расходы и существующий лимит; для нового лимита сначала восстановите категорию. Автоматического переноса лимитов на следующий месяц нет.

API: `GET /api/v1/profiles/{p}/category-budgets/{month}` возвращает категории, расходы, лимиты и их сумму; `PUT` и `DELETE` по тому же пути с `/{category_id}` управляют отдельным лимитом. Создание — без `version`; обновление/удаление — с текущей версией. При `409` редактор предлагает загрузить актуальные данные. Обзор включает эти показатели в поле `category_budgets` из того же снимка БД, что и общий бюджет.

Контракт: `api/openapi.json`, доступен также через `/openapi.json`. Профильный префикс — `/api/v1/profiles/{id}`. В JSON суммы передаются строками целых копеек, например `"125050"`; баланс и агрегаты также строки. Бюджет — месячный лимит расходов, а не банковский остаток.

При изменении контракта обновите Go-обработчики, проверки и типы:

```sh
cd frontend
npm run api:types
```

Postman-коллекция `postman/collections/FinTrack API` сгенерирована из OpenAPI. Папка `Smoke` проверяет финансовый цикл; **запускайте её против отдельной тестовой БД**, поскольку она создаёт два профиля и операции. Укажите URL Go API, подключённого к этой БД:

```sh
cd frontend
npx postman collection lint '../postman/collections/FinTrack API'
npx postman collection run '../postman/collections/FinTrack API' -i Smoke --env-var baseUrl=http://127.0.0.1:8002 --no-report-events
```

Локальная проверка работает без облачного workspace. Опция `--output` у установленного Postman CLI требует входа; обычный запуск выше этого не требует. Для перегенерации полной коллекции выполните `postman spec generate collection api/openapi.json -n 'FinTrack API' --folder-strategy Tags --force` из корня, затем `node scripts/build-smoke.mjs`.

Автоимпорт выписок, OCR, уведомления, Rust-клиент и мобилка остаются следующими этапами. Сейчас реализован ручной MVP.
