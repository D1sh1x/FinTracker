# VPS: доступ и обслуживание

## HTTPS по IP: доступ с телефона

18 октября 2026 добавлен публичный адрес **https://167.86.68.233:9443**. Он работает без домена, VPN, SSH-туннеля и включённого ПК. Общий логин — `owner`; пароль хранится на ПК в `.local/vps-access.txt`, на сервере — в защищённом `.deploy/access.txt`. В Git секреты не входят. Профили внутри приложения остаются по имени.

Отдельный сервис `gateway` в `compose.ip.yml` проксирует запросы к прежнему `frontend`. Он использует Caddy 2.11.7 и публичный IP-сертификат Let's Encrypt с профилем `shortlived`. Caddy автоматически обслуживает продление; сертификаты/ACME-аккаунт сохраняются в собственных томах `fintrack-vps_ip_tls_data` и `fintrack-vps_ip_tls_config`. Реальный выпуск и повторный старт с сохранённым сертификатом проверены; фактическое продление в будущем ещё не наблюдалось.

Порты только этого шлюза: TCP `167.86.68.233:9443` — HTTPS, TCP `167.86.68.233:80` — HTTP-01 challenge и редирект 308 на HTTPS. Порт 80 должен оставаться доступен для продления. HTTP-сайт финансовые данные не отдаёт. UDP/HTTP3 отключён. Прежние 443/8443/24443, VPN/ноды, контейнеры и маршруты сохранены; API и PostgreSQL наружу не опубликованы. Приватный `127.0.0.1:8088` для SSH остался прежним.

Для обслуживания с новым шлюзом используйте **все три файла**:

```sh
cd /home/avaki/finance-tracker
dc() { sudo -n docker compose -p fintrack-vps -f compose.yml -f compose.vps.yml -f compose.ip.yml "$@"; }
dc ps --all
dc logs --tail=100 gateway
dc restart gateway
dc up -d --no-build --wait
```

В серверной `.env` добавлены `FINTRACK_PUBLIC_IP`, `FINTRACK_PUBLIC_PORT`, `FINTRACK_ACCESS_HASH` (bcrypt-хеш в одинарных кавычках). Не выводите `.env`/пароли в логи. Для отключения публичного доступа достаточно `dc stop gateway`; работа сайта через SSH и данные БД сохранятся. Не применяйте `--remove-orphans` с сокращённым списком Compose-файлов: так можно удалить шлюз.

Проверка с ПК: `node scripts/check-public-access.mjs` читает секрет локально, проверяет TLS, анонимный 401, вход и read-only API/мобильный сайт. В некоторых сетях ПК HTTP:80 перехватывается/блокируется: редирект дополнительно проверен на самом VPS; основной адрес используйте с `https://` и портом `9443`.

APK и её подключение: [ANDROID.md](ANDROID.md). Ниже сохранены подробности первоначального приватного развёртывания и SSH-доступа.

## Открыть сайт с Windows

Приватный frontend слушает `127.0.0.1:8088`; публичный HTTPS обслуживает отдельный gateway. Для дополнительного SSH-доступа с ПК запустите туннель и откройте **http://127.0.0.1:18088**. Это приложение на VPS; локальная версия на `8088` остаётся отдельной.

После перезагрузки ПК или разрыва соединения откройте PowerShell в папке проекта:

```powershell
.\scripts\open-vps-tunnel.ps1
```

Оставьте терминал открытым. `Ctrl+C` закроет туннель; сервер продолжит работать. Не запускайте второй туннель на том же локальном порту. Если `18088` занят, используйте `-LocalPort 18090` и откройте соответствующий адрес.

Эквивалентная команда:

```powershell
ssh -N -T -i "$env:USERPROFILE\.ssh\engsider_friend" -o IdentitiesOnly=yes -o BatchMode=yes -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -L 127.0.0.1:18088:127.0.0.1:8088 avaki@167.86.68.233
```

API доступен через тот же адрес: `http://127.0.0.1:18088/api/v1`, OpenAPI — `/openapi.json`, readiness — `/health/ready`.

Серверная база новая: создайте профиль. Финансы из локального Docker, локальная `.env`, изображения и модели не переносились. Миграция этих данных — отдельная операция при необходимости.

## Что запущено

`compose.yml` + `compose.vps.yml` запускают собственные `db`, `migrate`, `api`, `frontend`, `backup`. Миграция `Exited (0)` — нормальное состояние. API/БД доступны только внутри Docker; фронт публикует только `127.0.0.1:8088`. Публичные 443/8443 остаются заняты существующими сервисами.

| Сервис | Лимит CPU | RAM | PID |
| --- | ---: | ---: | ---: |
| db | 0,75 | 512 MiB | 128 |
| migrate | 0,5 | 256 MiB | 64 |
| api | 1,5 | 768 MiB | 128 |
| frontend | 0,25 | 128 MiB | 64 |
| backup | 0,25 | 256 MiB | 64 |

Сеть `fintrack-vps_default`: `10.203.88.0/24`. Тома: `fintrack-vps_database`, `fintrack-vps_caddy_data`, `fintrack-vps_caddy_config`. Backup-файлы — `/home/avaki/finance-tracker/backups`. Ограничения не резервируют ресурсы: нагрузку при массовом OCR нужно оценивать отдельно. На другом сервере сначала проверьте конфликты портов и подсети; Compose с поддержкой `!override` обязателен (на этом VPS проверен v5.3.0).

На VPS есть нативный OCR из Go API, но **Qwen не развёрнут**. `QWEN_URL=http://127.0.0.1:8091` в контейнере сейчас недоступен: классификатор предупреждает об этом, неизвестные категории остаются «Не определено», строки можно исправить до подтверждения. Подключение модели, оценка CPU/RAM и качество OCR на сервере требуют отдельной проверки. Мобильное приложение ещё не реализовано.

## Команды на сервере

Войдите по SSH, затем задайте короткую функцию только для этого проекта:

```sh
cd /home/avaki/finance-tracker
dc() { sudo -n docker compose -p fintrack-vps -f compose.yml -f compose.vps.yml "$@"; }
dc ps --all
dc logs --tail=100 api frontend backup
curl -fsS http://127.0.0.1:8088/health/ready
```

Перезапуск и запуск уже загруженных образов:

```sh
dc restart api frontend
dc up -d --no-build --wait
```

Для остановки только трекера: `dc stop`. Возобновить: `dc up -d --no-build --wait`. Не используйте общесерверные `docker ... prune`, перезапуск Docker, изменение firewall или `down -v` для обслуживания приложения. Тома и существующие ноды/VPN должны сохраняться.

## Резервные копии

Backup выполняется при запуске и раз в 24 часа, хранит 7 дневных и 4 недельных копии. Последняя копия текущего дня/недели обновляется. Health check проверяет успешность и свежесть до 26 часов.

```sh
dc exec -T backup /bin/sh /scripts/backup.sh
cat backups/last-success
dc ps backup
ls -lh backups/*.dump
```

Восстановление для проверки выполняйте в **новую тестовую БД**, никогда не поверх `fintrack_go`:

```sh
# Замените дату на существующий файл; имя тестовой БД должно быть свободно.
dc cp backups/daily-YYYY-MM-DD.dump db:/tmp/restore-check.dump
dc exec -T db createdb -U fintrack fintrack_restore_check
dc exec -T db pg_restore -U fintrack -d fintrack_restore_check --exit-on-error /tmp/restore-check.dump
dc exec -T db psql -U fintrack -d fintrack_restore_check -c 'SELECT count(*) FROM profiles;'
```

После проверки тестовую БД можно удалить командой `dc exec -T db dropdb -U fintrack fintrack_restore_check`. Имя основной базы — `fintrack_go`; её не удаляйте. Реальная копия на VPS восстановлена и сравнена с исходной БД. Ошибка CRLF при первом запуске устранена; `.gitattributes` закрепляет LF для `*.sh` даже при Windows checkout/архивировании.

Копии пока хранятся на том же VPS: внешнее резервирование и уведомления о сбоях не настроены. Для копии на ПК используйте `scp`, подставив дату и локальное место хранения; дампы содержат финансовые данные, не добавляйте их в Git.

## Обновление

Сначала сделайте backup. Сохраните текущую версию `.env` локально на сервере в защищённом каталоге `.deploy` (не выводите её в чат/логи). Размещайте только исходники из Git, сохраняя `.env`, `backups/` и Docker-тома.

Задайте новый уникальный `FINTRACK_VERSION` в серверной `.env`, затем собирайте только образы трекера:

```sh
dc build api frontend
dc up -d --no-build --wait
curl -fsS http://127.0.0.1:8088/health/ready
```

Сборка на VPS потребует больше CPU/RAM, чем работа приложения. Для первого запуска образы собраны на ПК, экспортированы через `docker save`, переданы с проверкой SHA-256 и загружены `sudo docker load`; собственные имена образов — `fintrack-vps-api:<version>` и `fintrack-vps-web:<version>`. Старые образы оставляйте до проверки новой версии. Откат к прежним образам возможен только при совместимости схемы; обновления БД требуют отдельного плана восстановления из backup.

Проверка существующей инфраструктуры до/после сохранена на сервере в `.deploy`: у 16 работавших контейнеров не изменились ID, время старта и сети; все 22 старые сети и маршруты сохранены. Никакие пакеты, firewall, VPN или конфигурация Docker daemon при развёртывании не менялись.

## Доступ с телефона и дальнейшее развитие

Сайт доступен с телефона через HTTPS по IP с общим входом, описанным выше. Индивидуальных паролей профилей нет: общий вход открывает доступ ко всем профилям. Автоматизация резервирования вне VPS, уведомления о сбоях и Qwen остаются отдельными задачами.
